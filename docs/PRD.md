# Compose Manager 产品需求文档

## 1. 产品定义

Compose Manager 是一个单机、Compose 优先的轻量级 NAS Docker 管理面板。主要用户是在绿联 NAS、群晖 NAS 或 Linux 主机上维护 5–50 个 Compose 项目的家庭和小团队管理员。

核心任务不是覆盖 Docker 的每一个对象，而是让用户在默认首页快速回答四个问题：哪些项目正常、哪些项目需要更新、每个项目消耗多少资源、现在可以执行什么日常操作。

## 2. 成功标准

- 1440×900 桌面视口内可见 15–25 个紧凑行（展开行会降低数量）。
- 打开首页后一次 API 聚合即可展示项目状态、容器数量、资源和访问地址。
- 已有 Compose 项目无需通过本产品创建即可发现。
- 任意 Compose 编辑失败都不改变当前可用文件。
- 所有危险动作有明确确认，且后端再次验证前置条件。
- Docker 不可用时系统仍能启动并给出可诊断错误，而不是崩溃。

## 3. 信息架构

左侧一级菜单仅包括：

1. Compose（默认）
2. 项目文件
3. 容器
4. 镜像
5. 更新进度
6. 更新记录
7. 设置

顶部只有一行系统摘要：CPU、内存、Compose 数量、容器运行数/总数、镜像数、预计可清理空间。

## 4. 功能需求

### 4.1 Compose 总览

每行展示项目名称、运行状态、正常容器/总容器、CPU、内存、镜像更新状态与操作。访问通过行操作按钮提供。状态语义：绿色正常，黄色存在更新，红色停止或异常，灰色未运行。

支持按名称搜索和按运行/停止/异常/有更新筛选；支持展开项目查看容器名称、状态、镜像、CPU、内存、端口和启动时间。

行内操作：启动、停止、重启、更新、编辑、访问、日志、更多。停止、重建、恢复版本等危险操作必须明确显示影响范围。

### 4.2 自动发现

系统必须识别非本产品创建的项目。发现优先级：

1. Docker 容器 labels：`com.docker.compose.project`、`project.config_files`、`project.working_dir`、`service`。
2. 配置的扫描根目录中 `compose.yaml`、`compose.yml`、`docker-compose.yaml`、`docker-compose.yml`。
3. label 与扫描结果按规范化绝对路径和项目名合并。

无法定位配置文件的 label 项目仍可展示和执行容器级只读操作，但禁止进行文件编辑或 Compose CLI 操作。

### 4.3 Compose 文件编辑

主要模式为源码编辑器，支持 YAML 高亮、行号、搜索、自动缩进和基础 YAML 校验。保存流程：

1. 解析请求且验证路径位于允许根目录。
2. 比较客户端基准版本，防止覆盖并发修改。
3. 将候选内容写入同目录临时文件。
4. 对候选文件执行 YAML 解析和 `docker compose -f <temp> config --quiet`。
5. 展示服务端生成的 Diff。
6. 创建带时间戳和哈希的备份及历史记录。
7. 原子替换原文件。
8. 若为“保存并应用”，执行 `docker compose up -d`，随后检查容器状态并记录结果。

仅保存与保存并应用都要保留历史；支持预览历史、比较和恢复。恢复本身也要先备份当前版本并重新校验。

第一版快捷修改仅覆盖 image/tag、ports 和 restart，且最终仍通过同一保存管线。`.env` 读取时默认脱敏；不在更新日志中保存环境变量内容。

### 4.3.1 Compose 工作区与项目创建

项目文件页面只浏览部署时挂载并配置为 Compose 根目录的路径，不是通用 NAS 文件管理器。支持进入子目录、创建文件夹，以及编辑 Compose YAML、`.env`、JSON、TOML、INI、CONF 等常用文本配置；二进制和其他文件只显示，不允许网页编辑。所有保存均比较 SHA-256、创建备份并原子替换。MVP 不提供文件删除、移动或上传。

Compose 首页提供“新建 Compose”入口。用户选择允许根目录，填写小写项目名、根目录内相对路径和 `compose.yaml` 源码。服务端拒绝绝对路径、`..`、符号链接逃逸和已存在的目标目录；在正式落盘前执行 YAML 与 `docker compose config` 校验。用户可选择仅创建或创建后执行 `up -d`。

工作区与扫描配置保存在 NAS 服务端；任何能够访问面板并完成登录的电脑看到相同数据，不依赖创建项目时使用的客户端电脑。

### 4.4 容器

容器页采用高密度小卡片网格，桌面端默认每页 24 个，显示名称、状态、所属 Compose 项目、CPU、内存、镜像、Tag、端口和操作。顶部用单行概览显示总数、运行中、已停止和有更新数量，并可直接作为筛选入口。筛选包括全部、运行中、已停止/异常、有更新、非 Compose 容器及 Compose 项目。操作包括启动、停止、重启、更新和日志。

### 4.5 镜像与安全删除

每个镜像显示 Repository、Tag、Image ID、Digest、大小、创建时间、运行容器引用、停止容器引用、Compose 文件引用及远端更新状态。

自动分类：使用中、Compose 已引用、旧版本、未使用、Dangling、疑似更新残留。系统估算可释放空间，但禁止默认自动清理。

删除前确认页和服务端执行时都必须重新统计三类引用。运行容器引用大于零时拒绝删除；停止容器或 Compose 引用存在时默认拒绝，用户只能在明确的强制流程中继续，MVP 不开放强制删除入口。

### 4.6 更新检查

系统启动后立即执行一次镜像更新检查，此后默认每 24 小时自动检查。本阶段不提供手动检查入口，也绝不因检查结果自动升级。检查通过本地 RepoDigest 与远端 registry manifest digest 对比，将结果汇总到 Compose 项目、容器和镜像列表。Docker Hub 检查优先复用 Docker Engine 已配置的 HTTPS registry mirrors，避免管理面板与 Docker daemon 的网络路径不一致；私有仓库、限流或缺少本地 Digest 时明确显示等待检查状态。

发现更新后，必须由用户在具体 Compose 项目上确认更新操作。

统一更新流程：检查 → 记录旧镜像 ID/Digest → pull → 确认成功 → up -d → 健康检查 → 记录结果。更新由后台任务执行，左侧“更新进度”页面轮询展示等待、下载镜像、重建容器、状态检查与完成/失败阶段，并允许展开查看经过限制和脱敏的命令输出。记录时间、项目、服务、原/新镜像、原/新 Digest、结果和错误摘要。数据模型保留回滚所需字段，但 MVP 不承诺一键回滚。

### 4.7 内网与外网访问

解析 Docker 端口映射并使用 NAS IP 生成 `scheme://host:port/path`。用户可为端口配置显示名、默认路径、协议及是否显示快捷按钮。

外网访问 MVP 支持自定义 URL、域名和端口。通过 `RemoteAccessProvider` 接口保留 UGREENlink、Lucky、Cloudflare 等扩展。第一版不依赖 UGREENlink 未公开 API。

### 4.8 设置

设置项：Docker Socket、Compose 扫描目录、NAS 内网 IP、默认协议、镜像仓库、外网访问、页面紧凑度、深/浅主题。镜像更新默认每 24 小时自动检查。

## 5. 安全与可靠性

- 浏览器只能访问本产品 HTTP API。
- 不提供执行任意命令的 API；Compose 命令由操作枚举映射到固定参数。
- 所有 ID、项目名、服务名和路径均验证。
- 使用 `filepath.Rel`/规范化路径防止 `../`、符号链接逃逸和 Windows 路径变体。
- 写文件采用临时文件、同步、备份和原子替换；校验失败只删除临时文件。
- 更新、保存、恢复、删除和启停写入审计事件。
- API 错误不回显敏感环境变量或 registry 凭证。
- 首次启动必须使用一次性初始化密钥创建唯一管理员账号；初始化完成后不再开放账号创建。
- 密码使用 Argon2id 独立随机盐哈希；不得保存明文密码或可逆密文。
- 登录使用服务端会话和 HttpOnly、SameSite=Strict Cookie；所有写 API 校验与会话绑定的 CSRF 令牌。
- 登录失败按来源与用户名限速；登录、初始化和退出写入审计记录，日志不得包含密码或会话令牌。
- 建议部署层继续提供 TLS 和来源限制；MVP 不把“无 TLS 暴露公网”作为支持场景。

## 6. MVP 与后续边界

### MVP

- 单 Docker Engine、单管理员部署。
- Compose 发现、总览、资源统计、启停重启、日志。
- Compose 源码编辑、校验、Diff、备份、历史、恢复和应用。
- 受限 Compose 工作区、常用配置编辑和新建 Compose 项目。
- 镜像列表、引用关系、可清理估算、安全删除。
- 每 24 小时自动检查镜像更新，以及必须由用户确认的更新流水线。
- 内网快捷地址、自定义外网地址、Provider 接口。
- SQLite 配置与审计记录、单容器部署。
- 单管理员首次初始化、登录、退出、会话过期与 CSRF 防护。

### 后续

- 一键镜像回滚、计划更新与通知。
- UGREENlink、Lucky、Cloudflare Provider 实现。
- Registry 凭据管理与更完整的语义版本建议。
- SSE/WebSocket 推送（MVP 的任务进度采用短轮询，后续可改为服务端推送）。
- 密码修改/恢复、只读用户和可选双因素认证。

### 明确不做

应用商店、Swarm、Kubernetes、SSH、SFTP、允许根目录之外的通用文件管理、文件上传/删除/移动、Nginx 管理、证书签发、DNS、完整 NAS 管理、高级网络/卷编辑、多租户、企业 RBAC。

## 7. 非功能需求

- 单实例内存目标低于 150 MB（不含 Docker CLI 子进程和前端浏览器）。
- 常规列表 API 在 50 个项目/200 个容器规模下目标 P95 < 1 秒（资源采样可使用短期缓存）。
- 所有长操作具有超时与互斥锁；同一项目不并发执行更新/应用。
- SQLite 启用 WAL、busy timeout 和迁移版本。
- 支持 amd64/arm64 镜像构建。
